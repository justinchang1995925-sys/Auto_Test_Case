# 通用异常注入库（EX 库）与交叉选点

> 本文件定义**可复用的通用异常事件**（急停、低电量、定位丢失等）及其与业务测试点的**交叉选点规则**。
> 编号说明见 [SKILL.md](SKILL.md)「编号体系」；维度归属口径见 [SKILL.md](SKILL.md)「安全维度的两个子域」。

## 定位：EX 不是第四级追溯主键

`EX-ID` 与输入文档一样，**只是「需求来源目录」**，不进追溯链。链路仍是三级：

```
EX-002（库条目）→ 实例化为项目 REQ-0NN（来源列写「异常注入库 EX-002」）→ TP → TC
```

因此六维度、`REQ→TP→TC` 体系、思维导图层级、审计脚本前缀逻辑**全部不变**。新增一个异常事件只需改本文件（EX 表加一行 + 矩阵加一行 + 按矩阵补用例），`SKILL.md` 与 `templates.md` 不用动。

## 维度归属：按后果判，不按「是不是异常」判

异常事件**不归入单一维度**，按「失效的直接后果」拆到两个维度（口径见 [SKILL.md](SKILL.md)「安全维度的两个子域」规则 4）：

| 后果 | 归属维度 | TP 号段 | 测试类型 | 覆盖类型标签 |
|------|---------|---------|---------|-------------|
| **伤人 / 损机** | 安全（功能安全子域） | `TP-SEC-101~199` | `安全测试` | `功能安全-触发` / `功能安全-恢复` |
| **功能不可用 / 数据不一致 / 任务失败** | 稳定性 | `TP-S-xxx` | `稳定性测试` | `异常` / `反向` |

**不新增测试类型、不新增第七维度**——两类都有现成枚举值且 TP 前缀天然对齐，硬门禁第 14 项（维度一致性）自动通过。

**单格升级规则（强制）**：某个交叉格若在该阶段会引发人身/设备伤害（如低电量导致夹持失效使工件跌落、定位丢失导致机器人失控移动），则**该格单独升级为功能安全**，改挂 `TP-SEC-1xx`、测试类型改 `安全测试`、覆盖类型用 `功能安全-触发/恢复`——升级是**按格**的，不改变该 EX 的默认归属。升级须在矩阵「判定依据」列写明升级原因。

## EX 库条目

### 字段规范

| 字段 | 规范 |
|------|------|
| EX-ID | `EX-{三位序号}`，全局唯一，只增不改（废弃条目标「已废弃」，不回收编号） |
| 事件名称 | 简短名词短语，如「急停触发」 |
| 归属维度 | `安全（功能安全）` 或 `稳定性`，按后果判 |
| 事件类型 | `瞬时动作`（一次性触发后进入某状态）/ `持续状态`（存续期间系统需持续应对）/ `渐变`（多级阈值逐步加剧） |
| 触发方式 | **必须可操作**，写清怎么造出这个事件（含真机与模拟两种途径），严禁写「模拟低电量」这类不可执行描述 |
| 可注入时机 | 该事件在哪些阶段原型下可被注入，是交叉选点的候选来源 |
| 预期骨架 | 该类事件的预期结果必须写到的要素，交叉用例在此基础上按阶段补充「该阶段特有的副作用处置」 |
| 解除方式 | 事件如何结束、是否需人工干预、是否需二次确认 |
| 适用产品形态 | 哪类产品需要纳入（无该形态特征的项目可整条标 N/A，须写理由） |
| 默认优先级 | 本体用例的建议优先级，交叉用例按所处阶段的风险单独定级 |
| 引入依据 | 安规条款 / 历史缺陷单号 / 产品硬性要求，用于评审时说明「为什么要测这个」 |

### EX-001 急停触发

| 字段 | 内容 |
|------|------|
| 归属维度 | **安全（功能安全）** `TP-SEC-101~199`，测试类型 `安全测试` |
| 事件类型 | 瞬时动作 → 进入持续安全态 |
| 触发方式 | ① 面板急停旋钮按下；② 外部急停回路断开（拔掉安全插头 / 断开外部急停线）；③ 软件急停指令（如产品提供）。**三种触发源须各自 ≥1 条用例**（覆盖深度最低标准要求） |
| 可注入时机 | ST-1 空闲、ST-2 运动/导航中、ST-3 夹持工件中、ST-4 任务执行中、ST-5 数据写入中、ST-6 恢复过程中（**全阶段可注入**——安全停止必须能覆盖任何正在执行的动作） |
| 预期骨架 | ① **停止时限**：≤{X}ms 内所有运动轴停止、抱闸生效（X 需产品/安规给值，未给则用例标 Blocked）；② **状态上报**：状态码 / 告警 / 日志留痕，上位机与 APP 均可见；③ **恢复行为**：解除后所处状态，**严禁自动恢复运动** |
| 解除方式 | 旋钮复位（或回路恢复）+ **二次确认**才退出急停态；复位后未确认前不得响应运动指令 |
| 适用产品形态 | 一切带运动部件的整机 / 机器人 / 智能硬件 |
| 默认优先级 | P0 |
| 引入依据 | 安规强制项（功能安全），失效直接伤人 |

### EX-002 低电量

| 字段 | 内容 |
|------|------|
| 归属维度 | **稳定性** `TP-S-xxx`，测试类型 `稳定性测试`（单格可按上文升级规则升为功能安全） |
| 事件类型 | 渐变（多级阈值：告警 → 功能限制 → 强制回充/安全关机） |
| 触发方式 | ① 真机放电至各阈值；② 调试指令注入指定 SOC 值（推荐，可重复且省时）。**各级阈值须分别注入**，不能只测最低一级 |
| 可注入时机 | ST-1 空闲、ST-2 运动/导航中、ST-3 夹持工件中、ST-4 任务执行中、ST-5 数据写入中 |
| 预期骨架 | ① **分级阈值行为**：每级阈值对应的动作与限制（哪些功能被禁用）；② **告警上报**：告警等级、文案、上报通道；③ **任务处置**：进行中的任务是暂停/中止/允许完成，进度是否保存；④ **恢复**：充电后能否续作、是否需重新下发任务 |
| 解除方式 | 接入充电 / 电量回升越过阈值，自动解除；须验证解除后限制项确实放开 |
| 适用产品形态 | 电池供电的移动设备 / 移动机器人 |
| 默认优先级 | P1 |
| 引入依据 | 现场高发（任务中途断电导致任务失败、进度丢失） |

> **ST-3 夹持工件中升级提示**：若该产品在低电量强制关机时**会失去夹持力导致工件跌落**，则 ST-3 格升级为功能安全（`TP-SEC-1xx` / `安全测试`），预期须含「保持夹持力至安全放置完成」或「关机前先执行安全放置」。若产品为机械自锁夹爪（断电仍保持夹持），则不升级，仍按稳定性测任务处置即可——**升级与否取决于机械实现，须在矩阵判定依据中写明依据来源**。

### EX-003 定位丢失

| 字段 | 内容 |
|------|------|
| 归属维度 | **稳定性** `TP-S-xxx`，测试类型 `稳定性测试`（单格可按上文升级规则升为功能安全） |
| 事件类型 | 持续状态（可恢复） |
| 触发方式 | ① 遮挡定位传感器（激光/视觉镜头遮挡）；② 断开定位数据源；③ 进入无特征/强反光区域；④ 注入低置信度定位数据。**至少覆盖一种物理遮挡 + 一种数据注入** |
| 可注入时机 | ST-2 运动/导航中、ST-4 任务执行中、ST-6 恢复过程中；建图场景另按项目补充 |
| 预期骨架 | ① **检测时限**：≤{X}s 内判定为定位丢失（非无限等待）；② **降级动作**：安全停止或降速，**不得带着错误位姿继续执行运动**；③ **状态上报**：定位状态、告警、日志；④ **重定位/恢复**：自动重定位或人工干预方式，恢复后位姿正确性如何验证；⑤ **任务续作**：恢复后任务能否续作或须重新下发 |
| 解除方式 | 自动重定位成功 / 人工指定初始位姿；须验证恢复后位姿与真实位置一致 |
| 适用产品形态 | 依赖定位导航的移动机器人 / AGV |
| 默认优先级 | P1 |
| 引入依据 | 现场高发（定位漂移后继续执行导致撞机、任务点偏移） |

> **失控移动升级提示**：若定位丢失后产品**可能带着错误位姿继续运动**（而非停下），该格升级为功能安全——此时失效后果是撞机/伤人，不再是「任务失败」。

## 阶段原型（Stage Prototype）

不做「EX × 每个业务测试点」的全笛卡尔积（5 事件 × 40 测试点 = 200 条，不可维护）。先把业务测试点**聚成少量阶段原型**，EX 只与阶段原型交叉，规模压到 `|EX| × |阶段原型|`。

| ID | 阶段原型 | 特征（该阶段有什么东西需要被中断/保存/释放/回滚） | 代表性业务场景（每原型挑 1–2 个即可） |
|----|---------|------------------------------------------|--------------------------------|
| ST-1 | 空闲 / 待机 | 无进行中动作，无待保护资源 | 上电后待机、任务队列为空 |
| ST-2 | 运动 / 导航中 | 有运动惯量、有目标点、有路径 | 导航至目标点途中、关节点动中 |
| ST-3 | 夹持工件中 | **持有物料**，失去夹持力即掉落/损坏 | 抓取后搬运途中 |
| ST-4 | 任务执行中 | 多步流程进行到中间步，有已完成步骤与剩余步骤 | 多步装配/配送任务第 N 步 |
| ST-5 | 数据写入 / 上报中 | 有未落盘数据、未完成的上报事务 | 任务结果写入中、日志上报中 |
| ST-6 | 恢复 / 复位过程中 | 正在从上一次异常中恢复，状态机处于过渡态 | 急停解除后复位中、重定位进行中 |

阶段原型清单**可按项目增删**（如无夹持机构则删 ST-3 并在矩阵写明），增删须在交付的矩阵中说明。

## 交叉适用性矩阵（新增交付件，Phase 2 产出）

### 表头（固定）

| EX-ID | 事件名称 | 阶段原型 | 代表业务场景 | 适用性 | 判定依据 | 升级为功能安全 | 落地 TP-ID | 落地 TC-ID |
|-------|---------|---------|-------------|--------|---------|--------------|-----------|-----------|

- `适用性` 仅允许 `必测` / `选测` / `不适用`（**三值之一，严禁留空**）
- `判定依据` **全部三值都必填**（含「必测」，写为什么必测）
- `升级为功能安全` 填 `是（原因…）` / `否`
- 标 `不适用` 时 `落地 TP-ID`/`落地 TC-ID` 填 `-`

### 适用性判定规则（核心：不能硬加）

**标 `必测` 或 `选测` 的前提是同时满足以下三条**（AND，缺一即 `不适用`）：

1. **时机可达**：该阶段在真实运行中确实存在，且该事件在此阶段**可被注入**（EX 的「可注入时机」与该阶段有交集）。
2. **机制有耦合**：事件处理逻辑与该阶段的状态/资源**确实相互作用**——该阶段有需要被中断、保存、释放、回滚或联锁的东西。若事件在该阶段的处理与在空闲态**完全一样**（系统照常处理，没有额外副作用要管），即为**无耦合**。
3. **有独立可观测差异**：在该阶段注入的预期结果与其他阶段**不同**。若预期与已有某格完全一致，标 `不适用` 并写「等价于 {格}，已由 {TC-ID} 覆盖」。

> **反例（必须标不适用，不得硬凑）**：
> - 「ST-1 空闲 × EX-003 定位丢失」——空闲时不移动，无需中断任何动作，处理与「上电未定位」等价 → 不适用（无耦合 + 无差异）。
> - 「ST-5 数据写入中 × EX-001 急停」——若该产品数据写入与运动控制完全解耦（急停不影响写入事务），则无耦合 → 不适用；但若急停会切断写入进程电源导致文件损坏，则有耦合 → 必测。**同一格在不同产品上结论可以不同，依据必须写清。**
>
> 判定依据要写**机制层面的理由**（「该阶段无待释放资源，事件处理路径与空闲态一致」），不接受「不重要」「概率低」这类无机制依据的判断。

### 必测 / 选测 判定

候选格（通过上述三条）中：

- **必测**：该阶段存在**不可逆副作用**——物料损失、夹持物掉落、数据不一致/文件损坏、需人工干预才能复位、安全相关（任何升级为功能安全的格一律必测）
- **选测**：有耦合且有差异，但副作用可逆、可自动恢复

### 示例矩阵（EX-001~003 × ST-1~6，18 格全判定）

> 下例演示判定口径与写法，**不是可直接套用的结论**——同一格在不同产品上结论可以不同（取决于机械实现与软件耦合关系），落项目时必须按本产品实际重判并写清依据来源。注意其中 6 格为 `不适用`：**这是正确结果，不是遗漏。**

| EX-ID | 事件 | 阶段原型 | 适用性 | 判定依据 | 升级功能安全 |
|-------|------|---------|--------|---------|------------|
| EX-001 | 急停 | ST-1 空闲 | 不适用 | 无运动可中断、无待释放资源，处理路径与本体用例完全一致；等价于本体，已由 `TP-SEC-101/102` 覆盖（规则 3 无差异） | 否 |
| EX-001 | 急停 | ST-2 运动/导航中 | 必测 | 存在运动惯量，需验证停止时限与停止距离；停不住即撞击，不可逆 | 是（本身即功能安全） |
| EX-001 | 急停 | ST-3 夹持工件中 | 必测 | 急停切电后抱闸/夹持力行为决定工件是否跌落，不可逆（物料损失 + 砸伤风险） | 是 |
| EX-001 | 急停 | ST-4 任务执行中 | 必测 | 多步任务中断于中间步，需验证已完成步骤保留、恢复后续作或重下发，需人工干预 | 是 |
| EX-001 | 急停 | ST-5 数据写入中 | 必测 | 本产品急停切主控供电，写入事务被截断可能导致文件损坏/记录半条，数据不一致不可逆。**若产品的写入链路与运动控制完全解耦（急停不影响写入），此格应改判不适用** | 是 |
| EX-001 | 急停 | ST-6 恢复过程中 | 必测 | 状态机处于过渡态，二次急停易导致状态错乱、卡在无法复位的中间态，需人工干预 | 是 |
| EX-002 | 低电量 | ST-1 空闲 | 不适用 | 分级阈值行为与告警已由本体 `TP-S-011` 在空闲态覆盖，无额外副作用要处置（规则 3 无差异） | 否 |
| EX-002 | 低电量 | ST-2 运动/导航中 | 必测 | 强制回充与当前导航目标冲突，需验证是否中止当前路径、能否安全抵达充电点 | 否 |
| EX-002 | 低电量 | ST-3 夹持工件中 | 必测 | 本产品为电磁夹爪，强制关机即失去夹持力导致工件跌落，须验证「先安全放置再关机」 | **是**（掉件伤人/损物，按单格升级规则升级） |
| EX-002 | 低电量 | ST-4 任务执行中 | 必测 | 任务被暂停/中止的处置与进度保存，充电后能否续作 | 否 |
| EX-002 | 低电量 | ST-5 数据写入中 | 必测 | 强制关机截断写入导致数据不一致，不可逆 | 否 |
| EX-002 | 低电量 | ST-6 恢复过程中 | 不适用 | **时机不可达**：EX-002「可注入时机」不含 ST-6，恢复过程为短时过渡态，无法稳定注入指定 SOC（规则 1） | 否 |
| EX-003 | 定位丢失 | ST-1 空闲 | 不适用 | 空闲不移动，无待中断动作，处理与「上电未定位」等价（规则 2 无耦合 + 规则 3 无差异） | 否 |
| EX-003 | 定位丢失 | ST-2 运动/导航中 | 必测 | 可能带错误位姿继续运动导致撞机，须验证检测时限内安全停止/降速 | **是**（失控移动，按单格升级规则升级） |
| EX-003 | 定位丢失 | ST-3 夹持工件中 | 不适用 | 本产品夹持与移动不并发（先到位停稳再抓取），该阶段不移动，定位丢失无待中断动作（规则 2 无耦合）。**若产品支持边搬运边导航，此格应改判必测** | 否 |
| EX-003 | 定位丢失 | ST-4 任务执行中 | 必测 | 任务点位偏移导致作业到错误位置，恢复后须验证续作点位正确性 | 否 |
| EX-003 | 定位丢失 | ST-5 数据写入中 | 不适用 | 定位模块与数据写入链路无耦合，定位丢失不影响写入事务，预期与空闲态一致（规则 2） | 否 |
| EX-003 | 定位丢失 | ST-6 恢复过程中 | 选测 | 重定位过程中再次丢失，需验证重试上限与不陷入死循环；可自动重试、副作用可逆 | 否 |

统计：18 格 = 必测 11 / 选测 1 / 不适用 6（按 EX 分：EX-001 五必测一不适用；EX-002 四必测两不适用；EX-003 两必测一选测三不适用）。**6 个不适用格不补用例、不计缺口**，但每格都写了机制层面依据，因此仍通过「未评估格 = 0」与「判定缺依据 = 0」两项门禁。

### 交付要求

矩阵作为**独立 Sheet**（中文名「异常交叉适用性矩阵」）汇入交付工作簿；同时它是 Phase 2 的**建模产物**——命中「存在通用异常事件交叉」场景时，必须先出矩阵再写用例（见 [templates.md](templates.md)「强制设计技法触发表」）。

## 用例落地规则

### 本体用例（事件自身）

每个纳入本期的 EX **必须有本体用例**，验证事件自身的检测、响应与恢复，挂到独立本体 TP：

| EX | 本体 TP 示例 | 说明 |
|----|-------------|------|
| EX-001 | `TP-SEC-101 急停触发后整机停止与状态上报`<br>`TP-SEC-102 急停解除与恢复确认` | 功能安全深度门禁要求触发与恢复各 ≥1 条；三种触发源各 ≥1 条 |
| EX-002 | `TP-S-011 低电量分级阈值行为与告警` | 各级阈值分别覆盖 |
| EX-003 | `TP-S-021 定位丢失检测与降级停止`<br>`TP-S-022 重定位恢复与位姿正确性` | 检测与恢复分开 |

### 交叉用例

- **编号**：`TC-EX-{模块缩写}-{三位序号}`，如 `TC-EX-GRIP-001`（夹持中急停）
- **TP 命名**：`{阶段} + {事件}`，如 `TP-SEC-111 夹持工件中触发急停`、`TP-S-023 导航移动中定位丢失`；前缀按该格的最终归属维度（含升级后）
- **模板**：走**普通主表**（一次执行即可判定，不像专项要 N 次采样）；测试类型按归属维度填 `安全测试` 或 `稳定性测试`
- **注入信息位置**：注入时机写进**前置条件**（如「1. 机器人已抓取工件并处于搬运途中」），注入动作写进**操作步骤**中的独立一步
- **预期**：EX 预期骨架 + **该阶段特有的副作用处置**（如 ST-3 加「工件保持夹持不掉落」、ST-5 加「已写入数据完整、无半条记录」）。步骤与预期仍须一一对应、条数相等

### REQ 归属（D2：异常侧 + 交叉基线列）

| 项 | 规则 |
|----|------|
| **REQ 主归属** | 交叉用例挂**异常侧 REQ**（由 EX 实例化的 REQ，来源列写「异常注入库 EX-00X」）。理由：该用例验证的是**异常处理是否正确**，业务场景只是载体 |
| **业务侧信息** | 统一写进**三张表各自现有的「备注」列**，固定前缀 `交叉基线：`，格式 `交叉基线：ST-{n} {阶段名} / {业务REQ-ID}`，如 `交叉基线：ST-3 夹持工件中 / REQ-012`。**主表、附表、追溯矩阵表头一律不新增列**（三表表头固定；统一前缀便于筛选与审计脚本按前缀解析） |
| **不双挂** | 交叉基线**不进**矩阵的 `REQ-ID` / `TP-ID` 列，矩阵每行仍是「单 REQ → 单 TP → 单 TC」，**不触发硬门禁第 11 项②「多 REQ 共用一条 TC」** |
| **业务侧覆盖不受影响** | 业务 REQ 自身的正向/反向覆盖照常由业务用例满足；交叉用例**不计入**业务 REQ 的覆盖深度（避免用一条交叉用例冒充业务反向覆盖） |

### 优先级

- 交叉用例按**所处阶段的风险**单独定级，不直接继承 EX 默认优先级（如「空闲态低电量」可 P2，「夹持中低电量」应 P0/P1）
- **安全类（含升级格）用例不计入 P0≈10% 的分布约束**，但须在优先级合理性评估中单列数量并说明（见 [SKILL.md](SKILL.md) Phase 4.4）

## 审计门禁（Phase 4 增量）

| 门禁项 | 计算口径 | 阻断 |
|-------|---------|------|
| `EX 无本体用例数 = 0` | 本期纳入的 EX 全集 − 已有本体 TC 的 EX 集合 | 是 |
| `交叉矩阵未评估格数 = 0` | 矩阵中「适用性」列为空或非三值枚举的格 | 是 |
| `矩阵判定缺依据数 = 0` | 「判定依据」列为空，或为「不重要/概率低」等无机制依据的表述 | 是 |
| `必测交叉缺口 = 0` | 矩阵中标「必测」的格集合 − 追溯矩阵中已落 TC 的 (EX, 阶段原型) 对 | 是 |
| `EX-ID 引用非法数 = 0` | 用例/REQ 引用的 EX-ID − EX 库全集（防引用不存在的事件） | 是 |
| `交叉用例占比` | 交叉 TC 数 / 总 TC 数，建议 ≤15%，超出须说明原因 | 否（软提示） |

> **门禁只管「每格都评估过且理由充分」，不要求每格都有用例**——标「不适用」且依据充分的格**不计入缺口**。这是为了防止为凑覆盖率硬造无意义的交叉用例：硬凑的用例会稀释真实风险、拖长执行时间，比漏测更难发现。

## 新增一个 EX 的操作步骤

1. 本文件「EX 库条目」加一节，字段填全（触发方式必须可操作、预期骨架必须可判定）
2. 按后果定归属维度（伤人/损机 → 安全；任务失败 → 稳定性）
3. 交叉矩阵加一行 × 全部阶段原型，逐格判 `必测/选测/不适用` 并写机制依据
4. Phase 1.2 的 A 组补一条「本期是否纳入 EX-00X」（决定 REQ 全集，必须进 A 组）
5. 实例化为 REQ → 建本体 TP/TC → 按矩阵必测格补交叉 TP/TC
6. `SKILL.md` 与 `templates.md` **不需要改动**
